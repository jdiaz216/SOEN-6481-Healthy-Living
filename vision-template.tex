\section{Introduction}

This document outlines Healthy Living's goals, stakeholders and features. It defines high-level requirements that will guide development and will keep it aligned with the needs of all stakeholders throughout the project life-cycle. Healthy Living is a web-based application that helps students plan meals, track groceries and discover recipes that fit their budget, schedule and cooking skill. It provides a single, easy-to-use platform for everyday meal management.

\subsection{User Environment}
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Student:} Accesses the web app from different types of devices (cellphones, tablets and laptops) from anywhere, with different internet connection speeds and can receive alerts and reminders on their smart devices. They can access the web app at any time of the day and the number of students can grow to millions.
  \item \textbf{System Administrator:} Accesses the web app from a desktop to maintain and fix issues with the backend infrastructure from a very secure network. They can access at any time of the day and the number of administrators is expected to stay under 10.
  \item \textbf{Content Moderator:} Accesses the web app from mobile devices as well, but mostly works from a desktop in the office, during office hours. The number of content moderators is expected to be under 10.
  \item \textbf{Support Specialist:} Accesses the web app from the office and from home to resolve issues and handle overall customer service, during office hours. The number of support specialists is elastic depending on user support needs, but is expected to start around 10.
  \item \textbf{System Integration:} The application will integrate with existing APIs to retrieve food information, such as nutrition data and ingredients.
\end{itemize}

\section{Product Overview}

\subsection{Product Perspective}
Healthy Living is a stand-alone web application. It is not part of a larger internal system or product line and it does not depend on any other in-house product to function. It has one shared database behind it, storing meal plans, grocery lists, recipes, user accounts and support tickets.

While the product is self-contained, it does interface with external systems. Healthy Living integrates with existing third-party APIs to retrieve food-related data, such as nutrition facts and ingredient information, rather than maintaining this data manually. This keeps recipe and nutrition content accurate and up to date without extra work from the Content Moderator.

Students access the web app directly through a browser, on any device. Administrators, Content Moderators and Support Specialists access the same underlying web application, but through different URLs and user interfaces suited to their responsibilities. All four roles interact with the same central database, so information (such as a moderated recipe or a resolved ticket) is reflected consistently across the system.

\section{Product Features}

\subsection{Student Features}
\begin{enumerate}[leftmargin=1.7em]
  \item \textbf{Account Registration and Login:} A student can create an account and sign in, so their meal plans and preferences are saved and kept private.
  \item \textbf{Student Profile and Preferences:} A student can save their diet, allergies and cooking skill, so the web app can suggest things that fit them.
  \item \textbf{Grocery Budget Setting:} A student can set how much they want to spend on groceries, so meal plans stay within their budget.
  \item \textbf{Meal Plan Creation:} A student can plan meals for a day or a week, so they know what to eat ahead of time.
  \item \textbf{Meal Plan Editing:} A student can change or remove planned meals, so the plan can adjust to a busy week.
  \item \textbf{Weekly Calendar View:} A student can see all planned meals for the week in one place.
  \item \textbf{Automatic Grocery List Generation:} The web app builds a grocery list from the meal plan, so the student does not have to figure it out themselves.
  \item \textbf{Grocery List Editing and Check-off:} A student can add, remove, or check off items while shopping, so the list is updated.
  \item \textbf{Recipe Search and Filtering:} A student can find recipes by ingredient, difficulty or time, so they can find something they can actually cook.
  \item \textbf{Recipe Suggestions Based on Meal Plan:} The web app suggests recipes that match the student's plan, budget and skill, so they spend less time deciding.
  \item \textbf{Recipe Nutrition and Allergen Information:} A student can see nutrition facts and allergen warnings on a recipe, so they can make safe choices.
  \item \textbf{Save and Rate Recipes:} A student can save favorite recipes and rate ones they have tried, so good recipes are easy to find again.
  \item \textbf{Alerts and Reminders:} A student gets reminders to plan meals or go shopping, so they are less likely to forget.
  \item \textbf{Historical Data Charts:} A student can see charts of past activity, like calories eaten over past weeks, so they can track progress over time.
  \item \textbf{Seasonal Food Recommendations:} The web app recommends seasonal food that is cheaper to buy, so students can save money.
  \item \textbf{Student-Created Support Tickets:} A student can open a support ticket if something goes wrong with the web app, so they can get help directly.
\end{enumerate}

\subsection{System Administrator Features}
\begin{enumerate}[leftmargin=1.7em, start=17]
  \item \textbf{System Health Monitoring:} An administrator can see uptime, errors and system load, so problems are identified early.
  \item \textbf{User Account Management:} An administrator can suspend, restore or remove accounts, so account issues get resolved quickly.
  \item \textbf{Access Control and Permissions:} An administrator can control who can see or do what in the system, so each role only has access to what it needs.
  \item \textbf{Event Log Viewing:} An administrator can view event logs, so they can analyze and understand system issues.
\end{enumerate}

\subsection{Content Moderator Features}
\begin{enumerate}[leftmargin=1.7em, start=21]
  \item \textbf{Recipe Review and Approval:} A moderator can check a recipe before it is published, so students only see recipes that are accurate and safe.
  \item \textbf{Recipe Editing:} A moderator can fix ingredients, steps or nutrition info, so the recipe has accurate information.
  \item \textbf{Recipe Removal for Safety:} A moderator can take down a recipe that is unsafe or wrong, so bad content is not visible.
  \item \textbf{Recipe Tagging and Categorization:} A moderator can organize recipes with tags and categories, so students can find what they need.
  \item \textbf{Flagged Content Review:} A moderator can review recipes reported by students, so user concerns get addressed.
  \item \textbf{Recipe View and Usage Reports:} A moderator can see reports on how recipes are viewed and used, so they know what content works best.
\end{enumerate}

\subsection{Support Specialist Features}
\begin{enumerate}[leftmargin=1.7em, start=27]
  \item \textbf{Support Ticket Management:} A specialist can receive, track and respond to student tickets, so issues get resolved in an organized way.
  \item \textbf{Student Account Visibility:} A specialist can view relevant account details, so they can solve a reported issue faster.
  \item \textbf{Issue Escalation:} A specialist can send technical issues to an administrator or content issues to a moderator, so the right person can resolve them.
  \item \textbf{Support Reporting and Metrics:} A specialist can see ticket volume and trends, so support staffing can be planned as the user base grows.
\end{enumerate}

\section{Other Product Requirements}

\subsection{Applicable Standards}
\begin{itemize}[leftmargin=1.5em]
  \item Web accessibility guidelines (e.g., WCAG) should guide the frontend.
  \item Data protection and privacy practices apply to student data, including dietary and health-related information.
\end{itemize}

\subsection{Platform and Hardware Requirements}
\begin{itemize}[leftmargin=1.5em]
  \item The web app must run in any modern web browser, on desktop, tablet and mobile, with no installation required.
  \item The backend must run on infrastructure that can scale to support millions of student accounts.
\end{itemize}

\subsection{Performance Requirements}
\begin{itemize}[leftmargin=1.5em]
  \item Common student actions, such as checking off a grocery item or viewing a recipe, should take less than 100 milliseconds, even on a slow mobile connection.
  \item The system must stay responsive with a student base that can grow into the millions.
\end{itemize}

\subsection{Design and External Constraints}
\begin{itemize}[leftmargin=1.5em]
  \item The four user roles (Student, Administrator, Content Moderator, Support Specialist) must stay clearly separated, each with access only to what they need.
  \item The web app depends on external APIs for nutrition and ingredient data, so it must handle cases where that data is delayed or unavailable.
\end{itemize}

\subsection{Documentation Requirements}
\begin{itemize}[leftmargin=1.5em]
  \item A short user guide for students, covering account setup, meal planning, groceries and recipes.
  \item In-app help and tooltips for key actions, such as building a meal plan or checking off groceries.
  \item Internal documentation for Administrators, covering deployment, backups and monitoring.
  \item Release notes for each update, summarizing new features, fixes and known issues.
\end{itemize}
